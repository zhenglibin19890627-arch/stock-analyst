## 一、背景与事实基线（PM 核查，全部有日志/代码证据）

1. **故障表现**：08-09 / 08-10 两日，资金流采集对东财的全部路径持续失败——直连三层"东方财富三层全失败"29 次 / 67 次；akshare 备用源（stock_individual_fund_flow，底层仍东财）失败 23 次 / 55 次。PM 逐条统计：**78 次 akshare 失败 100% 为 RemoteDisconnected**（连接层被掐断），无 KeyError/JSONDecodeError 类解析错误 → 非接口改版，判定为反爬/连接拦截类。
2. **既有结论**：019B 批次已排查过东财问题，结论"间歇性反爬阻断，非永久封禁/接口变更/频率封 IP"；`_http_get_em()`（data_collector.py L187-250）已内置多轮重试 + UA 池 + 随机延迟 1.5~3.5s + 直连/代理回退，但近两日仍全失败，说明既有策略未覆盖本次拦截模式。
3. **对照证据**：同期新浪系接口全部正常——sina_main 资金流今日入库 23 行真实数据（is_estimated=0 参评）；HSI 指数东财接口 Connection aborted 后降级新浪源采集成功（08-10 17:49 日志）→ 拦截**特定于东财域名**，与本机总出口、akshare 库本身无关。
4. **不在本批次范围**：akshare 版本升级（现 1.18.53，最新 1.18.84）。PM 呈报已说明升级属"长期保健"、非治本次病，监理本条仅批诊断；升级如需做，另行立项。

## 二、批次目标

1. **定位**当前拦截根因，给出证据链：IP 级拦截 / 请求头指纹级 / 频率级 / 本机网络代理环境因素，四者中判定主因；
2. **验证**至少一种可恢复访问东财 fflow 数据的策略（或实证"现有手段均不可恢复，需等待自然恢复/换出口"——这也是有效结论）；
3. **产出诊断报告与策略建议**。本批次**只诊断、不落地**：任何对生产代码/配置的应用改动须另立批次、经监理批准。

## 三、工作内容（诊断项）

- **T1 基线复现**：对 push2his / push2 两个 fflow 端点做最小化请求（各 ≤5 次），确认当前失败签名仍为 RemoteDisconnected，记录完整异常栈。
- **T2 策略矩阵**（每个策略 ≤10 次请求、串行、间隔 ≥3 秒）：
  - a. UA 与请求头组合（现 UA 池外扩、补 Referer/Accept/Accept-Encoding 等常见浏览器头、尝试完整浏览器头组 vs 极简头组对照）；
  - b. 端点对照（用东财其他接口如行情 quote API 测试，区分"域名级拦截"还是"fflow 接口级拦截"）；
  - c. 直连 vs 系统代理 vs 显式代理环境变量三态对照（`_http_get_em` 已有代理回退逻辑，查其实际走了哪条路、代理目标是否可达）；
  - d. 间隔梯度（现有 1.5~3.5s vs 更长间隔小样本对照）。
- **T3 本机网络环境排查（只读）**：查系统代理配置、DNS 解析结果、到东财域名的连通性（ping/nslookup 类只读手段）；**禁止修改任何系统级网络设置**。
- **T4 akshare 层对照**：同一会话内调用一个新浪系 akshare 接口（如 stock_zh_index_daily）成功、再调 stock_individual_fund_flow 失败，固化"库本身正常、问题在东财侧"的对照证据。
