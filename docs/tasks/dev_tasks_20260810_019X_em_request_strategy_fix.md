## 一、背景一句话

东财 WAF 对本机出口 IP 实施窗口式连接级丢弃（关窗持续 2~4 分钟）。现有重试间隔 1.5~3.5 秒全撞在窗口内白费；16:10 单窗口高密度触发加剧收紧；代理路径实测 0/8 无价值。本批次按裁定实施三项修复。

## 二、改动范围与子任务（仅 3 个文件：config.py / modules/data_collector.py / modules/daily_report.py）

### T1 拉长失败重试退避（对应建议 a-1）

- 改 `_http_get_em`（data_collector.py 约 L187-250）：**轮间重试等待由 uniform(1.5, 3.5) 秒改为 30s → 60s → 60s（各加 ±15% 随机抖动）**，轮数由 3 提到 **4**（仅本函数内部参数，**不得修改全局 `MAX_RETRIES = 3`**——它同时服务新浪/腾讯源的 `@retry` 装饰器）。
- 效果口径：单源最坏重试窗口约 3~4 分钟，与 019W 实测「30 秒间隔 2 分钟内可捕获开放窗口」一致。
- 批内逐只错峰延迟（`_EM_INTER_DELAY_RANGE` 1.5~3.5s）与六项机制常量**一律不动**。
- 注意交互：`_EM_FALLBACK_TOTAL_CAP_SECONDS = 600` 软超时不变；退避拉长后若触发软超时截断，未处理股票沿用现有补采链路（019Q M-5 补采清单），**不得为迁就退避而放大软超时**。自测报告中须给出「退避拉长 × 批内只数 × 软超时」的时序推算。

### T2 采集错峰拆分（对应建议 a-2）

- 改 daily_report.py 调度：16:10 单批全量 → **16:10 / 16:40 / 17:10 三个时间窗**，每窗采集资金流东财清单的 **1/3**（按代码排序固定切分，保证可复现）。
- 窗 1、窗 2 只做采集不生成报告；**窗 3 采集完成后执行一次完整日报流程**（日报生成 → P3-B 预警扫描 → 延迟补采注册 → 指数刷新），挂载顺序与现状完全一致。
- 实现形态：窗 2/窗 3 用一次性 daemon Timer 注册（与 `_schedule_capital_retry` 同型）；`_schedule_next()` 改为在窗 3 结束后注册次日 16:10。
- 并发防护：复用 `_generate_lock`；若后一窗触发时前一窗未结束，跳过并记日志，剩余股票由补采链路兜底。
- **不变项**：周日 20:00 权重优化定时器、30 分钟延迟补采机制、启动日志文案。

### T3 放弃代理路径（对应建议 a-3）

- config.py 新增开关 `EM_USE_PROXY = False`；`_http_get_em` 依据开关只走直连，代理分支与 `_proxy_health` 检查**保留代码、开关跳过**（留回滚能力，不删代码）。

## 三、红线（违反即打回）

3. 零写库（正常采集除外）；不得引入新依赖。
