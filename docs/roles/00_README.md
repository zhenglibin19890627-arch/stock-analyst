## 二、协作流程（各角色独立执行，不交叉兼职）

```
① 产品经理（Chats）签发任务书
        ↓
② 架构师（Quests）独立评审技术方案 → 出具评审意见
        ↓
③ 监理（用户）批准方案
        ↓
④ 开发人员（Quests）独立编码 + 自验
        ↓
⑤ QA（Quests）独立测试（不依赖开发自验） → 出具测试报告
        ↓
⑥ 产品经理 + QA 双签验收
        ↓
⑦ 监理批准关闭
```

### 独立性保障原则

| 原则 | 说明 |
|---|---|
| **PM 不兼架构** | PM 签发任务书后，技术方案设计/评审由架构师独立完成 |
| **PM 不兼测试** | PM 验收基于 QA 的测试报告，不再自行执行全部核验命令（PM 仅做交付物完整性检查） |
| **架构师不编码** | 架构师只设计方案和评审，不直接写实现代码 |
| **开发不自测验收** | 开发只做自验（确认代码能跑），正式验收由 QA 独立执行 |
| **QA 不依赖自验** | QA 独立设计测试用例、独立执行测试，不以开发自验报告为准 |

## 三、新窗口激活指引

| 角色 | 激活方式 | 推荐模型 |
|---|---|---|
| **架构师** | 新开 Quests 窗口，首条消息粘贴 `03_architect.md` 全文 | glm5.2（复杂任务可 kimi k3） |
| **QA** | 新开 Quests 窗口，首条消息粘贴 `04_qa.md` 全文 | glm5.2 |
| **开发** | 新开 Quests 窗口，粘贴 `docs/tasks/dev_prompt_B批次号.md` | 按任务类型匹配（见上方模型表） |
| **产品经理** | 当前 Chats 窗口已激活，无需重复 | glm5.2 |

## 四、新增角色触发机制

| 触发条件 | 新增角色 | 模式 | 决策方 |
|---|---|---|---|
| 数据源扩展至美股 / 3+ 市场 | 数据工程师 | Chats | 监理 |
| 部署复杂化（多用户 / 云端） | DevOps 工程师 | Chats | 监理 |
| 看板 / 报告可视化需求升级 | UI/UX 设计师 | Chats | 监理 |

> 触发时由产品经理起草角色定义文件，监理批准后补充至本目录。

### 新增角色激活流程

```
① 触发条件出现（监理或产品经理识别）
        ↓
② 产品经理起草新角色定义文件（命名：05_xxx.md / 06_xxx.md）
        ↓
③ 监理批准角色定义
        ↓
④ 补充至本目录 + 更新本 README 角色矩阵
        ↓
⑤ 按模式激活（Chats 直接对话 / Quests 新窗口粘贴定义文件）
```
