## 1. 修复①（N01，P1）：看板 trader 摘要读取面 live 兜底（captain 选型①）

**根因回顾**：日报期预计算的 `key_factors.trader` 摘要（stage_name/has_disagreement/
top_action）是看板 chip/⚡分歧/行动清单 overview 的唯一落库面；批次后报告被刷新覆盖
（021K 过期重评/手动刷新 → generate_advice 内 019A 回写）时，key_factors 被
`_build_key_factors`（不含 trader）整体覆盖 → 看板一面沉默、个股页 live 一面仍报警。

**修复设计（零写库、不碰 019A、B24 合规）**：

- **共享兜底函数** `modules/trader_advisor.py::derive_trader_signal_summary(kf_json,
  stock_id=None)`：stored 摘要在场（stage_name 非空）→ 原样透出零现算；缺失/无效且提供
  stock_id → live 现算 `generate_trader_advice` 兜底（只读），输出与 stored 摘要同构；
  兜底失败静默回 None（不阻塞看板，退化回现状）。无 stock_id 不兜底——离线调用面行为不变。
- **三处消费面接线**（以 R2 报告清单为准）：
  1. `blueprints/portfolio/watchlist_scores.py`：`_derive_trader_signal(kf_json,
     stock_id=None)` 委托共享函数；端点对**有 ok 日报**的行传 stock_id 启用兜底
     （top_action chip + ⚡分歧标注 → portfolio.js 渲染面）；
  2. `modules/action_list.py::build_action_list`：新增 `live_trader_fallback=False`
     参数，概览 trader_stage/has_disagreement 缺失时兜底（`get_action_list` 端点路径
     传 True）；兜底摘要同步进入 `_rating_move_item`（评级变动项 reason 的 ⚡提示）；
  3. （导出面）`blueprints.portfolio` facade 再导出的 `_derive_trader_signal` 签名向后
     兼容（缺省不兜底，既有测试/调用零改动）。
- **纯函数契约不破坏**：`build_action_list` 默认关闭兜底（不触库不触网契约保持），
  既有 40+ 用例零改动全绿。

**测试锁定**（`tests/test_trader_fallback_021bs.py`，16 例）：中免形态回归（stored 缺
trader + live 止损已触发 → 看板 chip 仍显示「止损·56.16（已触发）」）；stored 优先
（live 哨兵断言不被调用）；live 不可用/异常静默回 None；无报告股不凭空造 chip；
行动清单默认关闭兜底；兜底进入评级变动 reason；N03 文案两断言。

stage_name/top_action）：在场 = **P2**（已调和，落库面次日批次合流）；兜底亦缺 =
P1（兜底链路回归或数据不足，需排查）。报告 §0②行与 P1 findings 段改为数据驱动，
t3 快照叙述（§0①/§1/§3/§4）加注标记。重跑：`N01 落库缺失 5 股（兜底在场 P2 5 /
兜底亦缺 P1 0）`，存档 `docs/reports/021bs_audit_r2_t4_20260923.md`。

### 3.2 R1 脚本 F01 基准面更新

`overview.has_disagreement` 核对基准：stored trader 在场 → 以 stored 为准（原契约）；
stored 缺失（N01 兜底形态）→ 以 **live 现算**为准（行动清单兜底应与 live 一致）。
重跑 F01 五数据流 0/0/0/0 ✓（兜底未引入新分歧）。

### 3.3 R1 脚本 R03 同数据日 K 线不一致的见证分级（t4 验证期新发现，非 t3 清单条目）

**现象**：t4 验证重跑时出现 5 条 R03 P1（广和通/美格智能/奥飞娱乐/赛意信息/舒泰神）：
存量报告（09-22 15:59 批次生成）`price_advice.current_close` 与现 raw_kline 收盘
同数据日不符（20.94→20.75 等，±0.3%~0.9%）。t2/t3 重跑均未命中——**数据在 t3 复审后
演化**：020I 补采/数据修订链在 09-22 收盘后重写了这批 K 线行（raw_kline 无时间戳列，
行被覆盖）。

**证据（双存储见证）**：`ratings_history.price_at_rating`（B12-T2 契约：取 rating_date
当日 K 线收盘写入）与 `price_advice.current_close` 五股全部相等（20.94/48.1/9.16/
30.88/20.82）——报告与评级行系同一 K 线时点的两次落库，彼时自洽；现 K 线不同 ⇒
**K 线事后被修订**，属数据修订型时点差（报告重生成自愈），非代码矛盾。与审计既有
doctrine 一致（R09/R14「数据在报告生成后变更 → P2 避免误报为代码矛盾」）。

**处置**：R03 断言化分级——同数据日不一致时核对生成时点见证（witness
rating_date==report_date 且 price_at_rating==current_close）：一致 = **P2**（K线事后
修订型，无需修复）；见证缺失/不符 = **P1**（采集竞态，需排查）。selftest 新增 2 用例
（14 例全部通过）。文档化于脚本头 R03 规则文本。

**移交备注**：若「报告生成后 K 线被修订」常态化，可评估（a）报告生成改在 K 线定稿后
（批次时点后移），或（b）K 线修订后对当日报告的补偿刷新——涉批次时序，另立方案；
本轮按审计 doctrine 归类 P2 存档。今日 15:54 批次重生成后这 5 股自然合流。
