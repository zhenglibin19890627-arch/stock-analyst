## 一、结论摘要（根因分类）

**主因：东方财富侧 WAF 对本机出口公网 IP（183.134.206.110，浙江杭州电信家宽）实施「窗口式连接级丢弃」**（TCP 正常建立、TLS 完成后、HTTP 响应前被服务端掐断，表现为 100% RemoteDisconnected），丢弃窗口按分钟级时间推移开放/收紧，在采集批高密度请求时段（16:10 批）窗口长时间关闭，导致 08-09/08-10 两日 100% 失败。

**四类根因判定**：

| 类别 | 判定 | 证据摘要 |
|---|---|---|
| IP 级拦截 | **主因** | 直连与代理出口（Clash 对国内域名通常 DIRECT，同 IP）同窗口同失败；curl 原生栈同样存在全败窗口（`schannel: server closed abruptly`）；TCP/DNS/ping 全部正常，丢弃发生在 TLS 之后 → 服务端主动掐断，非网络故障 |
| 请求头/客户端指纹级 | 次因（加重因素） | 20:43:46-20:44:06 requests 9 连败期间 curl 2 连成；20:45:04-10 反向（curl 0/4、requests 5/9）→ WAF 对不同 TLS 指纹差异化丢弃，但非决定性（curl 也有全败窗口）；头组组合对拦截零影响 |
| 频率级 | 触发因素 | 两日失败 100% 集中在采集批窗口（08-09 11 时 23 次、08-10 16 时 19 次、17 时 36 次，合计 78 次，口径 A，见下表后注）；晚间低频测试成功率 33%，批窗口期 0%；窗口持续 2–4 分钟（T2e 实测） |
| 本机网络环境 | **排除** | 系统代理注册表正常（127.0.0.1:7897 监听中）、DNS 解析正常、TCP 443 连通、ping 0% 丢包、新浪系接口全正常（含 akshare 当日 8700 行）、代理对百度等一般站点可用 |

> **数字口径说明（可复现）**：本文「失败按小时分布」数字采用**口径 A**——统计对象为含 **「akshare备用源失败」** 的日志行，来源文件 **`logs\app.log.2026-08-09`** 与 **`logs\app.log`**（UTF-8 逐行匹配），按行首时间戳 `Substring(11,2)`（HH 字段）分组。复核命令（PowerShell，项目根目录执行）：
> ```powershell
> $all = @(); foreach ($f in @('logs\app.log.2026-08-09','logs\app.log')) { $all += Get-Content -LiteralPath $f -Encoding UTF8 | Where-Object { $_ -match 'akshare备用源失败' } }; "total: $($all.Count)"; $all | ForEach-Object { $_.Substring(11,2) } | Group-Object | Sort-Object Name | ForEach-Object { "hour $($_.Name): $($_.Count)" }
> ```
> 复核输出：`total: 78`、`hour 11: 23`、`hour 16: 19`、`hour 17: 36`，与本节 2.1「78 次」同口径。
> 备查**口径 B**（同两文件全部含 `RemoteDisconnected` 的行，含重试与直连层）：258 / 190 / 412，合计 860——不采用（含底层重试噪音，口径过大）。

**结论性质**：不是永久封禁、不是接口改版（无任何解析类错误）、不是 akshare 问题、不是本机网络故障。是**东财对爬虫行为的持续风控（连接级丢弃）**，与 019B 批次结论方向一致，但本批次实测丢弃窗口更长（分钟级）、频率更低，属于"反爬升级后状态"，当前处于**部分恢复状态**（夜窗口期约 40% 直连成功率，批窗口期 0%）。

## 二、证据链

### 2.1 事实基线（生产日志，PM 已核查 + 本批次复核）

1. 08-09/08-10 两日 akshare 备用源失败 **78 次，100% 为 RemoteDisconnected**，无 KeyError/JSONDecodeError（本批次 `Select-String` 复核 78/78）。
2. 直连三层失败原文：`2026-08-09 11:27:51,923 [modules.data_collector] WARNING [600276] 东方财富三层全失败（push2his/push2/akshare）...`
3. 新浪对照成功原文：`2026-08-10 16:44:29,056 ... 新浪 lscjfb 主力口径顶替成功: main=-52038.91 万（is_estimated=0，capital_source=sina_main...`（08-10 共 23 行 sina_main 真实入库）；`17:49:36 ... 恒生指数(HSI) EM 接口不可用(...RemoteDisconnected...)，降级新浪源`。
4. 失败按小时分布全部落在采集批窗口（口径 A，见第一节表后注）：08-09 11 时 23 次；08-10 16 时 19 次、17 时 36 次，两日合计 78 次。
5. 东财最近一次生产成功：08-06 14:00:12（proxy 路径）；08-04、08-05 各有 direct 成功。

### 2.2 本批次实测（54 次东财请求，全部串行、间隔 ≥2 秒）

1. **T1 基线**：push2his fflow 3 次内「成功-成功-失败」，push2 3 次全败——失败签名与生产完全一致；**证明当前非全断，存在开放窗口**。
2. **T2a 头组矩阵**：完整浏览器头/极简头/生产头 18 次结果与头组无关（第一轮 0/9、第二轮 6/9），拦截与请求头指纹无关。
3. **T2a-extra 指纹对照**：20:43:46-20:44:06 requests 9 连败、curl 2 连成（TLS 栈不同：OpenSSL vs Schannel）；20:45:04-10 倒置。**WAF 按客户端指纹差异化丢弃，随时间窗口漂移**。
4. **T2b 端点对照**：同一时刻 quote/kline/www 5/5 全通（真实行情 f43=134886 贵州茅台），fflow 端点独有高丢弃率 → **接口级规则比域名级更严**。
5. **T2c 三态对照**：直连 0/3、显式代理 0/3、env 代理 0/3；代理错误为 `ProxyError('Unable to connect to proxy', RemoteDisconnected)`——**代理出口同被丢弃**；代理对百度 200（代理本身正常）。
6. **T2d/T2e 间隔梯度**：15 秒间隔 1/3；30 秒间隔 ×5 为「成-败-败-败-成」（2/5），**窗口持续约 2–4 分钟后开放**，周期重试可捕获。
7. **T3 网络排查**：注册表代理 127.0.0.1:7897（verge-mihomo 监听中）、DNS 正常（push2his 解析随轮询变化：140.207.67.156 → 117.184.38.143）、TCP 443 通、ping 0% 丢包、出口 IP 为杭州电信家宽。
8. **T4 akshare 对照**：同一进程新浪 `stock_zh_index_daily` 8700 行成功（末行 2026-08-10），东财 `stock_individual_fund_flow` ProxyError 失败。

### 2.3 关键时序推论

- 丢弃发生在 **TCP 建立成功 + TLS 完成后、HTTP 响应前**（urllib3 栈：`getresponse → _read_status → RemoteDisconnected`），且服务端不返回任何 HTTP 错误码 → 典型的 WAF/防火墙「静默掐断」，非限流 429、非 403。
- 窗口期与生产批时间强相关（白天批 0%、夜间低密度 ~33-40%）→ 东财对该 IP 的**连接级风控状态随请求密度动态恶化**，缓解后不立即释放（08-10 16:44-17:27 连续 43 分钟全败）。

## 四、建议（供监理裁定，本批次不实施）

### a. 请求策略修复（可实施项，按优先级）

1. **拉长失败重试退避**：现 `_http_get_em`（data_collector.py L187-250）失败重试间隔 1.5~3.5 秒过短——本批次实测窗口持续 2~4 分钟，短间隔重试全部撞在窗口内。建议失败后改为 **30~60 秒指数退避，总重试窗口拉长至 3~5 分钟**（与 T2e 验证结果一致：30 秒间隔 2 分钟内即可捕获窗口）。此参数在 `MAX_RETRIES` 机制内调整，不改架构。
2. **批量错峰**：16:10 采集批 23+ 只股票单窗口高密度触发——建议**拆分到 16:10/16:40/17:10 三个时间窗分批**（每窗约 1/3 股票），降低单窗口请求密度，避免触发 WAF 收紧。
3. **放弃代理路径**：本批次实测代理出口（Clash 7897）对东财 0/8 全败（`Unable to connect to proxy`），生产 proxy 回退分支当前无价值；建议短期只保留直连路径，减少无效尝试（既省时间也减少请求密度）。
4. 请求头组：无修复价值（实测无效），维持现状即可。

### b. 网络环境修复（需用户操作，供监理评估）

1. **更换出口 IP（首选、见效最快）**：杭州电信家宽为动态 IP，重启光猫/路由器大概率获得新公网 IP；WAF 对新 IP 无历史污点，通常可立即恢复采集。操作：断光猫 2~3 分钟重拨 → `scripts/diag_019w_em_anti_crawl.py summary` + 单次探针验证。
2. **手机热点临时出口**：16:10 批窗口用手机热点（移动/联通网络）跑一次批，验证新 IP 下 fflow 成功率；仅作为应急手段。
3. **Clash 规则核查**：代理对东财的 `ProxyError` 疑为 DIRECT 规则导致同 IP 直连被丢（或规则 REJECT）。若在 Clash 面板中确认 eastmoney 规则为 DIRECT，可尝试临时改为走海外代理节点观察——**海外出口对东财 push2 是否放行未在本批次验证**（属风险项，仅作建议）。

### c. 建议等待自然恢复 + 监测方案（并行执行）

- **判断依据**：① 东财风控历史（019B 批次 08-03 结论）证明此类窗口数天~一周内自然收敛；② 本批次夜间实测已出现 33~40% 成功率的开放窗口，说明**风控烈度在下降**；③ 08-10 夜间 fflow 已能取到真实数据（贵州茅台 klines 完整返回）。
- **监测方案**：建议后续立项一个只读探针脚本（复用 `diag_019w_em_anti_crawl.py t1` 逻辑），每小时 1 次、每次 1 请求（每日 ≤24 次，远低于本批次 150 上限），记录成功率；**连续 3 个自然日成功率 ≥90%** 判定为恢复。
- **恢复后的自动补采**：东财恢复后，既有 019Q 回补机制自动补采缺日数据（R-4 约束），无需手动干预；以只读观察回补日志为准。

### d. 其他

1. **akshare 升级（1.18.53→1.18.84）对本次故障无帮助**：失败发生在连接层（RemoteDisconnected），与 akshare 版本无关；升级仍可作长期保健另行立项，但不作为恢复手段。
2. **根治性方案（需新依赖，另行立项评估）**：引入 `curl_cffi`（浏览器级 TLS 指纹模拟）或改用 HTTP/2 客户端——本批次实测 WAF 对客户端指纹有差异化丢弃（curl 窗口内通过现象），指纹模拟可能显著降低丢弃率；属新增依赖，须监理批准后另行立项。
3. **合规提示**：本批次全部请求 ≤150 次、串行、间隔 ≥2 秒，未加重封禁；批次后 EM 状态与本批次前一致（间歇窗口），无恶化迹象（T2e 末次 20:53 成功即证）。
