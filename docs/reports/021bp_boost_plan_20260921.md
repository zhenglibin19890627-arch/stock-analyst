## 二、范围① 市场扫描器（modules/market_screener.py，839 行）

### 2.1 纯函数清单（离线可复算，全部只读、不触网）

| 函数 | 签名 | 输入 | 说明 |
|---|---|---|---|
| `detect_signals` | `(kline_rows, wanted=None, window=3)` | `[{date, open, close, high, low, volume}]` 时间正序，len≥35 | 4 类金叉（macd_golden_above/below、kdj_golden_low/kdj_golden）→ `[{signal, label, trigger_date, note}]` |
| `detect_resonances` | `(hits, kline_rows=None, weekly_kline_rows=None)` | hits 为 detect_signals 输出；周K 同结构可选 | 4 组共振（res_double_golden/res_week_daily/res_bottom_reverse/res_zero_relay），买点型取最高档 |
| `_macd_series` | `(closes)` → (dif, dea) | close list，≥35 根 | 复用 `technical_detail._ema_list`，与评分口径同源 |
| `_kdj_series` | `(highs, lows, closes, n=9)` | | 种子 k=d=50，与 technical_detail._kdj 一致 |
| `_rsi_series` | `(closes, n=14)` | | Wilder RSI |
| `_ma_series` | `(closes, n)` | | 简单均线 |
| `apply_filters` | `(rows, filters=None)` | 快照行 dict list | 纯本地筛选引擎 |

**网络函数（勿在离线路径触碰）**：`fetch_sina_snapshot` / `fetch_industry_map` / `fetch_tencent_enrich` / `fetch_kline(symbol, count=120)` / `fetch_kline_weekly(symbol, count=60)` / `run_coarse_scan`（网络+库）/ `run_signal_chunk`（网络+纯函数，蓝图为 `POST /api/market/scan-signals`，blueprints/market.py L142）。

### 2.2 用自选股已采集数据离线复算——可行，字段映射表

| raw_kline（database/_db/_schema_core.py L71） | screener kline_rows | 备注 |
|---|---|---|
| `trade_date` | `date` | 唯一需要改名的字段 |
| `open/close/high/low/volume` | 同名 | 直接喂入 |
| `amount/turnover/pct_change` | （不需要） | screener 不消费 |

- `raw_kline_weekly` / `raw_kline_monthly`（020R-48B 起）：`{trade_date, open, close, high, low, volume}` → 周线共振波段（res_week_daily）所需 `weekly_kline_rows` **已采集、无需补拉腾讯周K**。
- 数量门槛：`detect_signals` 需 ≥35 根；共振③底背离需 ≥60 根、④二次金叉需 ≥50 根。`_read_kline_data(stock_id, limit=60)`（data_adapter.py L211）只够下限——**信号复算应自读 LIMIT 120~250**（KLINE_DAYS=250，库内存量足够），与评分读取解耦、互不影响。
- 现有读取参考：`data_adapter._read_period_kline_data(stock_id, table)`（表名白名单 raw_kline_weekly/raw_kline_monthly，升序返回）可直接复用于周K；日线需新写一个带 limit 的小读取（或给 `_read_kline_data` 传更大 limit）。
- 性能：100 只 × (读库+纯计算) 毫秒级/只，全程 <1s，对比腾讯在线拉K（`_QQ_MIN_INTERVAL=0.25s`/只 ≈ 25s 起步且有失败风险）**离线复算是净收益**。

### 2.3 红线注意

- 纯函数零副作用，不触 R5（网络超时包装）、R8（数据源耦合——输入是本地 DB 行，非 akshare 字段）。
- 结果属"快照参考"口径（扫描器边界约定）：**只产候选展示，不自动入库、不写 ratings/分析表**（与扫描器"只产候选不自动入库"同一边界）。
- 不碰 `BATCH_OPERATION_LIMIT=20`（R16）。

## 四、范围③ 每日报告（modules/daily_report.py，1771 行）

### 4.1 生成链路与概览表生成点

- `generate_daily_report(target_date, force, report_type, skip_collect, market_filter)`（L1178）→ 循环内 daemon 线程 + `t.join(timeout=STOCK_TIMEOUT_SECONDS)`（R18 合规模式）逐只调 `_process_single_stock` → 批末 `_build_markdown_summary(target_date, results)`（**L1581，概览表生成点**）→ 落 `reports/{date}.md`。
- `_process_single_stock`（L1024）返回键：`stock_id, symbol, name, status('ok'), engine, score, rating, score_change, reused, freshness{lines, has_issue}`；失败/超时仅 `stock_id/symbol/name/status('failed')/error`。
- `_build_markdown_summary` 概览表列：股票/代码/引擎/总分/评级/较前次；随后"数据完整度概览"（freshness.has_issue 的股）、评分异动（|score_change|≥5）、引擎统计、逐只详情（读回 daily_reports.markdown_content）。

### 4.2 各 result dict / 表列键名对照（决策闭环取数地图）

| 数据 | 键/列 | 出处 |
|---|---|---|
| 总分 | `score`（result）/ `total_score`（daily_reports 列） | daily_report / advisor |
| 评级 | `rating`；展示名 `rating_label` | 同上 |
| 评分变动 | `score_change`（对比 `_get_prev_score`） | daily_report L1114 |
| 四维分 | `key_factors` JSON：`{kline/fundamental/capital_flow/news: {score, weight, top_factors}}` | advisor._build_key_factors L523 |
| 操盘手摘要 | `key_factors.trader: {stage_name, has_disagreement, disagreement_text}` | daily_report L1122-1133（2026-09-18 预计算） |
| 趋势罗盘 | **不在 key_factors**——独立端点 `GET /api/stocks/<id>/trend` → `analyze_trends(StockData)` 返回 `{timeframes:{daily/weekly/monthly:{trend,score,strength,reasons}}, overall:{trend,score,strength,reasons,resonance}}` | modules/trend_analyzer.py（纯函数只读）；报告页 loadTrendCompass 异步填充（analysis.js L1359） |
| 位置分位（60日高低区间 0~1） | `trader_advisor._volume_structure` → `position_pctile`；条件化提示端点 `GET /api/stocks/<id>/position-note`（backtest_engine.position_note_for） | ⚠️ 与 price_advisor 的 `position_pct`（建议仓位%）**同名不同义**，接线时勿混淆 |
| 价格建议 | daily_reports.price_advice JSON（buy_range/target/stop_loss/take_profit/position_pct） | price_advisor 后处理（B24 合规模式） |
| 预警当日触发 | alert_history `UNIQUE(rule_id, stock_id, trigger_date)`，`trigger_date = 当日` 即当日触发集 | alert_engine |

### 4.3 报告页前端消费方式

- 生成入口在 analysis.js：`generateDailyReport()` POST /api/daily-report/generate + `pollReportProgress` 每 2s 轮询 `/api/daily-report/progress`（读 logs/report_progress.json）→ `renderProgressUI` 步骤时间线；完成后 `renderDailyReport`（看板融合版 banner + 刷新批量评分表）。
- `loadLatestDailyReport`（GET /api/daily-report/latest）为旧形态：`dailyContent` 容器不存在时跳过（日报已融合看板）。
- 个股报告页 `renderFullReport` 消费 `dimensions`（key_factors 重建）+ 四维 detail + trend/trader-advice 异步卡。

### 4.4 超时跳过的可见化机制（现状评估）

| 环节 | 机制 | 可见性评价 |
|---|---|---|
| 进行中 | `_update_progress_file/stage` → progress API → 前端进度条（含"当前在干什么"） | ✅ 充分 |
| 单只超时 | 写 daily_reports failed 行（error_msg='采集超时(90s)'）+ results 失败项 | ✅ 有记录 |
| 批末 | `failure_summary{total_failed, by_reason}` + markdown "> ⚠️ N 只生成失败" | ⚠️ **半可见**：概览表只列 ok_results，超时股从概览表消失；看板 banner 只显 fail_count 数字，by_reason 只在 POST 响应 JSON 里，用户需展开才见"哪些股被跳过" |
| 自愈 | 迟到 worker 落库覆盖 failed→ok（DELETE+INSERT）；次日批次 force 重算 | ✅ 数据不丢分 |

## 五、范围④ 批量分析端点（blueprints/watchlist.py L920 `POST /api/batch-analyze`）

- 调用方式：body `{stock_ids: [...]}`，**>20 直接 400**（BATCH_OPERATION_LIMIT，R16 风控，不可放宽）。前端 batchAnalyze()（watchlist.js L315）>20 弹"分批勾选"；021AZ 已有 `quickBatchAnalyze(stockId)` 单股直达。
- 流程：A股资金面批量预取（`fetch_capital_flow_batch`）→ 逐只 **同步串行**：`collect_stock_data`（全维度采集，秒级~90s+）→ `generate_advice` → `generate_price_advice` → 行业空缺补取。
- 耗时特征：无单只超时、无批次软超时、**无进度上报**（前端是假进度动画"逐只执行中"）；20 只满批典型数分钟。复用路径（B11 当日已有报告 + 当日已有采集记录）秒回，首采最贵。100 只 = 至少 5 次手动分批，体验断裂。
- 对照组：daily_report 已有完整的"单只 daemon 线程 join 超时 + 批次软超时 + 进度文件"三件套——批量分析端点一项都没有。
- 红线：R16 上限不动；R18（若加超时保护必须 daemon 线程模式，禁 `with ThreadPoolExecutor`）；SQLite 单写者 → 不做后端并发化；FLASK_DEBUG 保持 False。

## 八、四个优化项接线方案与建议

### 项 1：自选股买点信号离线复算（扫描器资产 → 决策闭环"信号"层）——**建议：做**

- **做法**：在 `modules/market_screener.py` 追加两个小函数（或独立 `modules/watchlist_signals.py`，推荐前者，信号库/共振库就在同模块）：
  1. `_read_kline_rows(cursor, stock_id, limit=120)`：raw_kline → screener 行格式（`trade_date`→`date` 映射，时间正序）；周K 复用 `data_adapter._read_period_kline_data(stock_id, 'raw_kline_weekly')`。
  2. `scan_watchlist_signals(stock_ids=None, signals=None, window=3)`：active 自选股逐只 `detect_signals` + `detect_resonances(hits, kline_rows, weekly_rows)`，返回 `[{stock_id, symbol, name, matches, resonances, kline_upto}]`。纯读库+纯函数，**零网络**。
- **端点**：`GET /api/market/scan/watchlist-signals`（挂 blueprints/market.py 现有 bp，零注册成本）；响应带口径标注 `"scope": "watchlist_offline"`（与扫描器"快照参考"边界对齐）。
- **复用签名**：`detect_signals` / `detect_resonances` / `SIGNAL_LIBRARY` / `RESONANCE_LIBRARY` 原样复用，不改其行为。
- **风险与红线**：低。只读不写库（不产候选入库）；不碰网络函数；结果标注触发日（trigger_date）避免与实时扫描混淆。
- **测试**：照 test_market_screener_021bi 模式 + test_routes 临时库模式，造 raw_kline 行（含 <35 根、≥60 根、周K 缺失降级用例）。**测试基建够用**。

### 项 2：预警链路接入信号类提醒（决策闭环"预警提醒"层）——**建议：做，且必须走现有幂等写入**

- **做法**：新增 alert_type（建议名 `signal_trigger`，阈值语义=共振星级门槛或勾选信号集）：
  - 按 §3.3 五处清单同步（alert_engine 3 处 + alerts.py 1 处 + alerts.js 2 处）；
  - 检查器内部调项 1 的复算函数（只读 raw_kline）；
  - 写入走现成 `INSERT OR IGNORE + UNIQUE(rule_id, stock_id, trigger_date)`——同股同日重复触发自动幂等，`scan_once()` 挂载点与双层异常隔离全部复用，不改 scan_once 主体结构（只经由 `_RULE_CHECKERS` 注册表扩展）。
- **复用签名**：`scan_once()` / `_get_active_rule` / `_format_message` / `_RULE_CHECKERS`。
- **风险与红线**：中低。R7：不做分数→评级重实现（本类型不涉评级）；V8：不回写源表；⚠️ 白名单**双处后端 + 前端标签**漏同步是最大踩坑点（API 400 / UI 裸 key）。
- **测试**：alert 域已有测试先例（幂等/规则优先级）；新增"同日二次扫描不重复插入"幂等用例 + 临时库造 K 线触发用例。**测试基建够用**。

### 项 3：行动清单（决策闭环"行动清单"层）——**建议：做，独立只读聚合端点 + 看板卡片，不改报告写库**

- **做法**：
  1. 新端点 `GET /api/dashboard/action-list`（挂 watchlist bp 或新聚合函数入 blueprints/portfolio/market 均可）：聚合四路现成数据——daily_reports 最新行（total_score/rating/score_change，含 status='failed' 的超时股显式列出，补 §4.4 可见性缺口）+ 项 1 信号复算 + alert_history 当日触发（trigger_date=今天）+ `trader_advisor` 摘要（key_factors.trader 已预计算，零重算）。
  2. 前端看板卡片（watchlist.js/portfolio.js 同域，或 analysis.js 看板区）消费，按"今日应做"排序：评级升级/降级 > 买点共振 ≥4 星 > 预警未读 > 超时缺报股。
- **备选（更轻）**：只在 `_build_markdown_summary` 概览表后追加"行动清单"markdown 小节——零新端点，但仅报告页可见、无法排序交互，**不推荐作为唯一形态**。
- **风险与红线**：R9 每日报告不变量不动（不碰 daily_reports 写入结构，聚合层只读）；`_build_markdown_summary` 若改，仅追加小节、不动 R9 相关写入路径；键名注意 §4.2 两个 position 同名不同义。
- **测试**：聚合函数纯逻辑单测（输入现成 dict/行构造）+ test_routes 冒烟。**测试基建够用**。

### 项 4：批量分析适配 100 只（"数据"层吞吐）——**建议：做（前端自动分批 + 后端进度可选）；不做后端并发化、不放宽上限**

- **做法（推荐，零红线风险）**：前端 `batchAnalyze()` 照 market.js `msStartSignals` chunk 驱动模式改造：全选 ≤100 只时自动拆 5×20 顺序 POST /api/batch-analyze，真实进度 = 已完成批数×20/总数；完成后合并 `renderBatchResults`。后端零改动。
- **可选增强（后端，独立可裁剪）**：batch-analyze 照 daily_report 三件套补进度文件（`_update_progress_file` 同型）+ 单只超时（daemon 线程 `join(timeout=STOCK_TIMEOUT_SECONDS)`，**严守 R18 禁 executor 上下文**）；批次软超时直接复用 `BATCH_TIMEOUT_SECONDS` 语义。
- **复用签名**：前端 `msStartSignals` 的 chunk/seq 驱动；后端 `daily_report._update_progress_file` / daemon 线程模式。
- **风险与红线**：R16 `BATCH_OPERATION_LIMIT=20` 不放宽（分批发生在前端多次调用，单次仍 ≤20，合规）；不做并发采集（SQLite 单写者 + collect 多源限频，并发会互相踩 R5/R2 的限速与链序）；R19 两个超时值语义沿用不改动数值。
- **测试**：前端拆批逻辑无法单测（项目无 JS 测试设施）→ 后端如做进度/超时，加 daemon 线程超时用例（test_scheduler_force.py 有 Timer 测试先例）；不做后端改动则零新测试。**测试基建对后端路径够用，前端靠既有路由冒烟兜底**。
