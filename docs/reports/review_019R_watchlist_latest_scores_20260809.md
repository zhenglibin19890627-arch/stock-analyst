## 二、逐项评审意见（对应评审重点 1-6）

### 1. SQL 实现方案：每股最新一份有效报告

**推荐：窗口函数（ROW_NUMBER）派生表 + LEFT JOIN。**

```sql
SELECT s.*, dr.engine_version, dr.total_score, dr.rating, dr.report_date, ...
FROM stocks s
LEFT JOIN (
    SELECT * FROM (
        SELECT dr.*,
               ROW_NUMBER() OVER (
                   PARTITION BY dr.stock_id
                   ORDER BY dr.report_date DESC,
                            CASE WHEN dr.report_type='daily' THEN 0 ELSE 1 END
               ) AS rn
        FROM daily_reports dr
        WHERE dr.status='ok'
    ) WHERE rn = 1
) dr ON dr.stock_id = s.id
WHERE s.status != 'delisted'
ORDER BY CASE WHEN dr.total_score IS NULL THEN 1 ELSE 0 END,
         dr.total_score DESC
```

（以上为推荐方案示意，最终 SQL 由开发实现并附口径注释。）

**理由**：
- 单次表扫描、无 N+1 子查询，符合"清晰、口径正确优先"的选型原则（任务书事实 7）；
- **daily 优先**（019D 口径）天然融入窗口排序键，无需额外函数判定——核验发现 08-06、07-31 两天**每股确实同时存在 daily 与 intraday 双行**（29 只 ×2），排序键的取舍不是理论问题，是现实数据；
- 派生表先 WHERE `status='ok'`（核验发现 07-24 存在 27 份 `status='success'` 历史旧值，证明过滤必要）；
- LEFT JOIN 天然保留"无报告股票兜底"（当前库 29 只全 active 无此场景，规则仍须保留）；
- 外部 ORDER BY 原样保留现有排序（无分排末尾、分数降序），零回归。

**备选**：相关子查询（每股 LIMIT 1）语义直观，但 N 次子查询；GROUP BY 自连接需额外处理"同日期双类型优先级"，不推荐。规模 481 行，窗口函数性能无忧。

**补充提示**：现有索引只有 `idx_daily_reports_date`（report_date 维度），每股最新查询模式是 `WHERE stock_id=? ORDER BY report_date DESC`，当前规模无碍；加 `(stock_id, report_date)` 索引属可选项，**本批次不做**（避免触碰库结构，登记风险）。

### 2. _resolve_report_type 多日期适配

**裁定语义：每股各自判定（逐股 daily 优先），不再全局判定。**

- 理由：全局判定（任一股票某日有 daily 就全员取 daily）在"每股日期不同"场景下**没有定义**——无法回答"08-09 该股没报告、08-07 该股有 daily"该取什么的问题；
- 逐股判定在"全库同日"时与全局判定**完全等价**（全库某日存在 daily → 每股该日也都有 daily），因此 019D 交易日口径零回归，任务书规则 3 可满足；
- 与 019D 的关系：019D 确立的"daily 优先 + status='ok'"**原则不变**，只是判定粒度从"按日全局"细化为"按股按日"；窗口排序键 `report_date DESC, daily 优先` 即该原则的逐股化表达，**无须再调用 `_resolve_report_type`**；
- 该函数本身保留不动，继续服务 `/api/ratings`（L1422-1470）、`report-latest`（L912/957）等单日期场景。

**辅助函数职责定义（新增，供开发实现；两接口共用，延续 019D"共享辅助防口径漂移"的设计意图）**：

- `_latest_report_join_sql()`：返回"每股最新一份有效报告"派生表的 SQL 片段与参数占位约定（含 status='ok' 前置过滤、daily 优先排序、rn=1 取行）；看板与汇总两接口**必须共用同一片段**，杜绝两处口径漂移；
- 不新增"按股判类型"的 Python 判定函数（SQL 排序键已覆盖，避免 Python/SQL 双处判定再次分叉）。

### 3. ETag 缓存语义

- **304 行为不劣化**：两接口 ETag 均基于"排除 `generated_at` 的整个 payload"（L1830-1833、L1993-1996）。改造后每行新增 `report_date`、顶层字段扩展，payload 内容变化 → ETag 自动失效 → 首次 200、此后 304，机制无需改动；
- **generated_at 语义须随口径同步**：现在取"全局最新日期 MAX(generated_at)"（L1914-1921、L1813-1819），多日期后应改为"每股最新报告集合中的 MAX(generated_at)"，保持"ETag 排除时间戳"的确定性不变；
- **向后兼容方案（裁定）**：顶层**保留** `report_date` 字段（单值，语义从"全库单一日期"平滑延续为"入选报告的最新日期"，旧消费方读到的是合理的"最新报告日期"），**新增** `report_date_min`（入选报告最早日期）；前端头部在 `min==max` 时显示单值、否则显示"min ~ max"。**不推荐**改为 `report_date_range` 字符串替换原字段（破坏兼容，且本无必要）；
- **行级新增** `report_date`（该股最新有效报告日期，无报告为 null），前端表格逐行展示。
